# Client architecture checkpoint: send decisions, test the player

## Decision this informs

Keep Cleanyfin's shared product metadata-only. The household library stays in Jellyfin. Treat a **supported player** as a particular version, playback mode and set of tested actions, not a Jellyfin-compatible logo. Proposed product contract: annotations describe a scene; the household authorizes what to do; the player must actually carry that decision out. This is not a claim that these layers all ship today.

| Boundary | Already here | What needs to be true before supporting a household |
| --- | --- | --- |
| Shared annotations | Go/SQLite segment API, voting and lookup | Untrusted marks are suggestions, not automatic parent-approved instructions. Keep media, viewing histories and household decisions out of the public database. |
| Household | Jellyfin library/users; Cleanyfin plugin resolves fingerprints and emits global `Unknown` segments | An authenticated, household-local resolver binds policy/approved revisions to the **selected edition, source and viewer**. A fingerprint alone is not proof that two cuts share timing. |
| Plan | Lab: a reviewed single cut bound to SHA-256 of one tiny fixture | Versioned source-time intervals, actions, validity and required capabilities. Never reinterpret mute as skip. A source/profile change invalidates the old plan. Do not label an unsupported, missing or expired plan as protected. Exact failure UX still needs a household decision. |
| Execution | Lab: one browser adapter, one aligned direct-play fixture | Receive original media from Jellyfin as usual; keep the forbidden interval out of the playback timeline *before presentation*. Evaluate other adapters separately. No automatic unfiltered fallback. |
| Verification | Lossless reference + rendered-frame/dominant-tone checks + seek test | Run the same fixtures against every claimed client/mode. Test partial fragments, cold resume, audio tracks, captions, changed source mid-play, and unavailable plans. Seek acknowledgements do not measure output. |

Local playback preparation in earlier experiments was a measurement reference, not a decision to fork a household's movies. The new browser experiment does **not** require storing an edited movie. It is cooperative and bypassable; server enforcement is a separate longer-term track. Federation, AI annotation and speech editing are independent of the first playback gate. Keep a small Go/SQLite deployment and avoid adding an online service per boundary.

## Browser experiment: one edited timeline, one unchanged source

Source: disposable Jellyfin Server 10.11.11 via authenticated direct stream; non-admin test viewer; desktop Chromium. No household server, AI, media proxy or modified stock playback bundle. A separate lab page in the disposable web root uses Media Source Extensions (MSE). Both control and candidate fetch identical synthetic H.264/AAC bytes. The in-memory player buffer contains the initialization data, first fragment, and time-shifted last fragment; it never appends the middle fragment. The `<video>` controls therefore see a shorter timeline. A source-time seek inside the omission maps to the first retained time after it. The fixture packaging index and edit plan are checked separately. Unsupported cuts are not rounded. Full-file SHA-256 verification and a 1 MiB cap are lab controls, not a scalable streaming protocol.

Fixture SHA-256 `438f960aa98f32526bf58b6536066ca0d21d46a5d529f6608559ead1dd5d25e9`. Three 80-frame sections, 25 fps, 440/880/660 Hz; middle is red. Nominal 3.2 and 6.4 s become **3.221406 and 6.421406 s on the muxed video timeline**. Ignoring that encoder offset would give the wrong seek boundary. Direct-stream duration 9.621406 s; filtered duration 6.421406 s. Control detected all 80 red frames and the 880 Hz marker; filtered output showed blue and green, zero sampled red or dominant 880 Hz, and a seek to source 4 s resumed on the green side instead of replaying the cut. Substituting a different Jellyfin item stopped playback with no source attached. The detector does not rule out faint AAC ringing, a physical output artifact, or an unsampled frame; do not generalize it to arbitrary word cuts.

**Negative control: an arbitrary mark.** The supported adapter rejected a one-frame change to the requested boundary without attaching a source. Separately tested a tempting alternative: use MSE append windows to remove only [4.021406, 6.021406), a middle portion of the red run. Append the same source twice: first with `appendWindowEnd=start`, then with `timestampOffset=start-end`, `appendWindowStart=start` and no end cap. The browser reported a single continuous buffered range. But the video-frame callback timestamps jumped from 3.981406 to 4.421406. Twenty intended red frames before the cut appeared; **zero of the ten allowed red frames after the cut** appeared before green. This controlled negative result rejects append windows alone as a frame-accurate solution for this GOP. It does not show all codecs/players have the same failure.

**Next engineering gate:** marks usually fall *inside* a GOP/audio packet, not conveniently on both fragment boundaries. Use a fixture with retained-picture/audio witnesses immediately adjacent to the marked interval. Compare a browser adapter capable of decoding from an earlier keyframe without presenting forbidden samples against a native player adapter; evaluate rendered output, preserved surrounding material, seek behavior and cost. Do not silently drop adjacent material. Live transcoding, HLS, multiple tracks/subtitles and per-profile plans remain unverified. Only promote to product integration once a real media mode meets the exposure and preservation requirements.
