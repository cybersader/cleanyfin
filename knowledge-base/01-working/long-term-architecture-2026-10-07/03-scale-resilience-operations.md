## Original summary

Research complete; requested Markdown-file delivery is blocked by the higher-priority developer instruction explicitly prohibiting report/summary/findings/analysis .md files. The complete assessment is returned below for parent synthesis instead. No repository files changed.

Verdict: retain a single local Go/SQLite service as the baseline, but do not equate the current scaffold with resilient operation, complete installation, federation, or reliable content enforcement. The first investment should be safe backup/verified restore, bounded exports, idempotent submissions, release packaging and honest failure semantics—not Postgres or distributed services.

The highest-consequence findings are unsafe hot-backup instructions; a connection pool that serializes reads as well as writes; unbounded full-corpus dumps; absent rate controls and submission idempotency; and plugin failure returning no segments. Current Compose deploys only the API, while the PWA requires separate tooling and the plugin manifest contains a placeholder checksum. Source inspection is not a live Jellyfin compatibility test.

A newly relevant dependency concern: the pinned modernc.org/sqlite v1.34.1 bundles SQLite 3.46.0. SQLite documents a rare WAL-reset corruption race fixed in 3.51.3 and selected backports. The current one-connection process alone does not satisfy its multi-connection prerequisites, but adding backup/read-pool/checkpoint concurrency warrants upgrading first.

Four explicit hypothetical workloads, transparent cost formulas, operational targets, failure controls, correction candidates and five reproducible future experiments follow. None of the sizing assumptions, availability goals, restore objectives or acceptance criteria are measured results or commitments.

WORKLOADS—ALL PROPOSED, NOT FORECASTS. Assume 20 segments/release, two retained votes/segment, 400 serialized bytes/segment, 1,000 stored bytes/segment including indexes and 250 bytes/vote. Household: 1,000 releases, 20,000 rows, 1,000 reads/day, peak 2 reads/s, 20 writes/day, burst 1 write/s. Small community: 10,000 releases, 200,000 rows, 100,000 reads/day, peak 20/s, 2,000 writes/day, burst 5/s. Public read-heavy catalog: 1,000,000 releases, 20,000,000 rows, 10,000,000 reads/day, peak 1,000/s, 100,000 writes/day, burst 50/s. Federated node: 100,000 releases, 2,000,000 rows, 1,000,000 reads/day, peak 100/s, 10,000 writes/day, burst 10/s, plus bounded peer imports. Reads model metadata lookups/scans, not every playback second; writes include votes/import changes. Skew, abuse and scans require separate burst tests.

TRANSPARENT COST MODEL. With F releases, s segments/release, N=Fs, V=2N: database estimate D=N×1,000+V×250 bytes gives 30 MB/300 MB/30 GB/3 GB respectively. Exact-lookup payload≈s×400=8 KB, giving raw daily query egress 8 MB/800 MB/80 GB/8 GB. Full raw dumps are 8 MB/80 MB/8 GB/800 MB. Hypothetical compression ratio 0.25—not measured—makes the public dump 2 GB. One hundred mirrors fetching daily cost 200 GB/day; hourly fetches cost 4.8 TB/day. A delta of 100,000 changed exported rows/day costs approximately 10 MB/mirror/day at the same ratio, excluding headers, tombstones and other record types. Monthly cost=host cost+stored-GB-month×storage rate+egress-GB×egress rate+operator hours×chosen internal rate. No vendor price or free-tier availability is assumed.

QUERY, WRITE, CACHE AND STORAGE BUDGETS. Origin database reads≈Q×(1−h), with h the cache-hit fraction; fronting-cache hits do not eliminate client-facing bandwidth. Single-connection occupancy≈read arrival rate×read connection-time+write arrival rate×write connection-time+export/import occupancy. If measured write time were 5 ms, 200 transactions/s is merely an ideal reciprocal, not capacity. WAL traffic≈writes/s×pages changed/write×4,096; 50 writes/s and six pages/write imply 1.23 MB/s, or 369 MB over five checkpoint-blocked minutes. Reserve disk for DB+WAL+export temporary files+restore workspace+retained backups; 30 GB DB, 8 GB raw export, 30 GB restore and two 30 GB backups already require 128 GB before headroom. Vote sums grow with votes/segment. Hash-prefix bucket payload scales with corpus size; it is not necessarily one release. Current LIKE query and plain BINARY index are mismatched with SQLite's default NOCASE LIKE optimization requirements: server/internal/store/store.go:96-98,181-184; https://sqlite.org/optoverview.html (accessed 2026-10-08). Verify EXPLAIN QUERY PLAN before claiming indexed performance; consider explicit hexadecimal range bounds.

VERSION AND CONNECTION TRADEOFF. SOURCE-VERIFIED: server/go.mod:8 pins modernc.org/sqlite v1.34.1; its versioned documentation identifies SQLite 3.46.0: https://pkg.go.dev/modernc.org/sqlite@v1.34.1. SQLite's WAL-reset race requires multiple connections plus a narrowly timed write/reset/checkpoint interaction; fixed versions include 3.51.3, 3.50.7 and 3.44.6: https://sqlite.org/wal.html#wal_reset_bug (both accessed 2026-10-08). Do not claim current reproduction or guaranteed exposure. PROPOSED: upgrade to a tested fixed engine before introducing connection/checkpoint concurrency. Then compare one connection with one controlled writer and a small reader pool, applying required pragmas per connection. Never put WAL on NFS/SMB or run multiple hosts against the same volume. More readers can prolong snapshots and WAL growth; busy_timeout is neither throughput nor request-deadline control.

BACKUP AND RESTORE. REJECTED: copying only the live main SQLite file, or sequentially copying changing DB/WAL files, as a consistent snapshot. SOURCE-VERIFIED: use SQLite Online Backup API or VACUUM INTO; alternatively stop all access, complete/verify a clean checkpoint/close, then copy the quiescent database. Never delete WAL manually. Sources: https://sqlite.org/backup.html and https://sqlite.org/wal.html (accessed 2026-10-08). PROPOSED backup command writes a temporary destination, completes and verifies it, then atomically marks the artifact usable; records application/schema versions, timestamp and digest; copies encrypted backup off-device. Restore into a new isolated location; check digest, integrity_check, foreign_key_check, expected counts and representative API reads/vote totals, then swap with rollback available. The public visible-only dump lacks raw votes, hidden state and future private policy/configuration, so it is not a complete backup. Integrity checks cannot substitute for application-level validation: https://sqlite.org/pragma.html.

Start private/loopback-bound; public contribution is opt-in. Provide doctor/backup/restore/upgrade commands and a UI showing readiness, free disk, last verified backup, source freshness and compatibility. BOUNDED EXPORTS AND FEDERATION. PROPOSED: build one versioned immutable export from a consistent snapshot, compress it once and serve a stored file using ETags/ranges; do not rerun full-table export per mirror. Paginate interactive lookups with stable keyset cursors and response/row/time limits. Pagination across mutable data needs an explicit snapshot revision, not merely OFFSET. Replication needs origin-stable IDs, monotonic revisions, tombstones, provenance, schema/version manifest, bounded download/decompression, transactional staging and atomic activation. Replaying an import must be idempotent; preserve local overrides outside imported namespaces. Peer outage must leave the last accepted local catalog usable. No importer, incremental protocol or federation guarantees are established by today's single JSON dump. A public dump is an interoperability ingredient, not operational federation.

RETRIES, ABUSE AND PRIVACY. PROPOSED: persist an idempotency key and payload digest with each accepted submission; repeat same payload returns original result, conflicting reuse returns 409. Current repeated POSTs create duplicates; vote replacement avoids duplicate numerical votes but arbitrary submitter IDs permit Sybil manipulation. Retry safe reads and idempotent writes only, honor Retry-After, use exponential full jitter with bounded attempts/total deadline, and never retry validation errors. Add connection/body/header/handler deadlines, inflight limits, bounded imports/exports and coarse burst limits with household-NAT tolerance. Admission must fail before unbounded queues consume memory. Current server sets only ReadHeaderTimeout: server/cmd/api/main.go:37-41. Log route templates, status, latency and error class—not fingerprints, prefixes, item IDs, tokens, submitted timestamps or IP-linked history. Current path logging records hash prefixes and segment IDs: server/internal/api/api.go:71-75. Short prefixes can still identify sparse buckets; exact fingerprints permit linkage.

CACHE, DEPENDENCY OUTAGE AND PLAYBACK. IMPLEMENTED plugin fetch deadline is ten seconds; failure returns an empty segment set, and category/action are not enforced by its output mapping: plugin/CleanyfinSegmentProvider.cs:58-91. Whether a failed refresh removes existing Jellyfin materialization is UNVERIFIED. PROPOSED local persistent last-known-good sets keyed by file/timeline identity, duration, schema and trust/policy revision; distinguish no data, stale data, revoked data and upstream failure. Validate before playback; expose stale age and per-household strict/cooperative choices. An unmodified client cannot be forced to stop because metadata is missing. Offline availability cannot promise fresh revocations or complete filtering. PWA has no service worker and no durable outbox: pwa/README.md:36-39. Its one-second interval can overlap requests and recomputes fingerprints every poll: pwa/src/main.ts:50-98. Fifty active markers imply about 100 Jellyfin requests/s and 6.25 MiB/s logical moviehash reads before caching, not measured disk I/O. Cache by item/file identity; use single-flight polling, cancellation and stale-position guards.

THREAT/FAILURE MATRIX. Process crash→restart plus recovery probe, not assumed durable power-loss recovery. Hung process→bounded operations and alert; Compose health does not establish self-healing. Disk full/read-only→reject writes explicitly, preserve reads where safe, reserve space and alert before exhaustion; never acknowledge failed commits. Corruption→quarantine read/write service and restore a verified copy, not overwrite the evidence. Power loss→explicitly select/test synchronous policy and storage guarantees. Long read→WAL growth/checkpoint lag alarm and bounded snapshots. Migration failure→retain old artifact/snapshot and stop with actionable repair state. Peer outage→last accepted local dataset and delayed sync. Malicious peer/dump→size/decompression/schema/signature validation and staging. Submission flood/Sybil votes→admission limits and local moderation authority. Wrong timeline/stale cache→reject unverifiable mapping and visibly report unavailable protection. Registry compromise→pinned verified artifacts and controlled upgrades. Current liveness always returns ok while readiness only pings DB: server/internal/api/api.go:89-100. Docker restart semantics: https://docs.docker.com/engine/containers/start-containers-automatically/ (accessed 2026-10-08).

MEASURED ESCALATION GATES. PROPOSED: first fix indexes, export isolation, cache behavior and query budgets. Evaluate Postgres only after a reproducible 30-minute peak workload still misses agreed latency/error objectives, with DB wait p95 >250 ms or sustained writer occupancy >70% for 15 minutes and evidence the writer—not encoding/network/disk capacity—is the bottleneck. Dataset row count alone is not the gate. Add a small read pool only after engine upgrade and comparative tests. Use a SQLite-backed job/outbox table before a broker; add a separate queue when demonstrated job concurrency/retry requirements cannot meet bounded latency within that design. Add replicas/failover only when rehearsed restore cannot meet the owner's chosen RTO and someone owns fencing, failover and drills. Rejected default: Redis, multi-writer federation, Kubernetes or distributed services introduced merely because the public-catalog scenario is large.
