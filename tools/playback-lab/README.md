# Playback lab

First test: given a start and end timestamp, remove that interval and nothing else. From the repository root on Linux or macOS with Python 3 and Docker:

```sh
python3 tools/playback-lab/check-cut.py
```

Docker downloads a pinned Jellyfin image on first use for its bundled FFmpeg. The test containers have no network, expose no ports and mount only the test's temporary directory. No Jellyfin account, household library, AI model, or private configuration is needed. The test removes its generated media when finished; Docker retains the cached image.

The six-second synthetic movie has three distinguishable pictures and tones. The middle two seconds are marked. The test makes a lossless reference edit, decodes both files, and checks that the output equals the original prefix plus suffix, byte for byte, separately for picture and sound. A missing allowed frame, an extra marked frame, or a changed audio sample fails the check.

This is a reference for what correct output looks like, **not a Cleanyfin playback implementation**. Its timestamps align with video frames and audio samples.

## Shared hard fixture: compare playback paths

The hard kit measures leaked and missing picture and sound against the same 20-second clip. Its one cut removes source frames 137–262 (5.480 to 10.520 s, end exclusive), inside both H.264 GOPs and AAC packets. The generator writes `source.mp4`, a lossless `reference.mkv`, and Kodi and mpv edit lists derived from `plan.json` (lab format v0, **not** a product contract). From the repository root:

```sh
python3 tools/playback-lab/hard-fixture.py NEW_DIRECTORY
python3 tools/playback-lab/analyze-capture.py --plan NEW_DIRECTORY/plan.json --video CAPTURE --audio CAPTURE --json
python3 tools/playback-lab/check-kit.py
```

Supply either or both capture options; pass the same recording to both to check both tracks. `--video` also accepts a directory of numbered images in one format, in capture order. Preserve the full picture so the frame barcode stays in view. Repeated frames are reported; backward jumps in source order fail. `--audio` accepts WAV or another media file, or raw `.pcm`/`.s16le` (48 kHz mono signed 16-bit little-endian). Audio times start at the first decoded sample; the detector reports 5 ms windows with a tone amplitude of at least 0.10 full scale and tolerates up to 5 ms of loss per neighbouring tone. This is a thresholded measurement, not sample-by-sample proof. `--json` adds the machine-readable result on the last line.

Use `python3 tools/playback-lab/hard-fixture.py --identifiable NEW_DIRECTORY` to add `identifiable.mp4` (the same H.264 pictures with lossless FLAC in MP4), `identifiable.plan.json`, and `identifiable-reference.mkv`. Each stereo sample pair uniquely identifies one source index. The kit self-test proves the exact oracle passes the reference and rejects both a single marked substitution and a one-sample-short output.

The desktop mpv checks capture decoded PCM and numbered pictures **from the same playback, with both tracks selected**. For a straight cut, the sound verdict compares both channels to the uninterrupted mpv decode with exactly the marked source sample indices removed. Length must match; no alignment adjustment is allowed. The verdict reports differences and their output index range. The unchanged 5 ms tone-window score is a coarse cross-check, not the kept-sound verdict. On the AAC fixture, the [joint run](prototypes/exact-audio/joint-receipt-2026-11-22.json) matched all 718,080 kept stereo samples and all 374 kept pictures, with no marked pictures or samples in the output. The earlier 448-sample discrepancy came from capturing with video disabled. The [FLAC controls](prototypes/exact-audio/README.md) show why that AAC pass does not extend to other sources or cut positions.

Passing the self-test says nothing about any real player until that player's output is captured and analyzed.

## Authenticated cut-list handoff (disposable lab only)

Run `python3 tools/playback-lab/check-plugin.py --case auth-range [--jellyfin 10.11|12.4]` from the repository root. `--jellyfin` (default `10.11`) picks one row of the `JELLYFIN` table in `hard_fixture_lab.py`: the server image by digest, the plugin's `JellyfinTarget` and the SDK image (9.0 or 10.0, by digest) move together, and the run checks the version the server reports. All six cases (with `marking` and `household-binding`) passed on both rows on 2026-11-24. Prerequisites: Docker, Python 3, the pinned Jellyfin image(s), the matching SDK image and the [desktop mpv lab image](prototypes/edit-list-players/README.md). The SDK restores build dependencies; set `CLEANYFIN_NUGET_FEED` to a pre-staged local NuGet package directory to run the build with `--network none` as well. The server and player share only a private loopback network namespace. No host port is published. The runner owns the synthetic source, hashes it and mounts that **one file** read-only. Do not substitute a mutable movie directory. On success the server and working data are removed; on failure the stopped container name and private local directory are printed. That directory includes Jellyfin's disposable authentication database; do not publish it.

The fixture-only issue endpoint is off by default. In the lab the descriptor and source have different short-lived bearer handles. Anonymous possession works until expiry or revocation; it is not proof of possession of the enrolled device. The plugin checks the viewer, device token hash, session, library rights, exact source and plan on each leg. Only Jellyfin's native static-file action sends movie bytes. At stock logging levels 10.11.11 printed the **native viewer token** at logout (`Emby.Server.Implementations.Session.SessionManager`, Information). The runner sets only that category to Warning before startup and scans server logs for all native test tokens and both capability values. HTTP logging remains at its defaults. Before considering a proxy, debug logging or another player, redact entire capability URLs (including paths), queries and auth headers at every layer. Completed reads and buffered bytes cannot be revoked.

A successful **handoff** does not certify editing fidelity. The runner separately checks the mpv picture sequence, sample-exact stereo PCM and the coarse tone windows, from the same play of the authenticated list URL. The uncut control also captures both tracks together. No PlaybackInfo override, pointer library, device eligibility or household playback is provided by this case.

### Read-only wireless debugging: private lab identity

The box sees **`cleanyfin@lab`**, not the operator's login or computer name. Stock ADB calculates that comment from the running process, not from the saved `.pub` text. The Linux lab uses a digest-pinned SDK 37.0.1 binary, a neutral hostname/login, a private key store and a dedicated ADB server on loopback inside its own network namespace. The host's Android home, physical USB bus and default ADB server are not mounted or reachable. A relay exposes only the exact numeric address and port the owner supplied; there is no discovery. Requires `bwrap`, `nsenter`, `setpriv`, `ip`, `ss` and `socat`.

1. **Qualify offline:** `python3 -IB tools/playback-lab/verify-adb-label.py` boots a disposable clone of the harness's API 36 Google TV image. Its neutral bootstrap key is different from the lab key. Only an actual wireless pairing followed by a matching guest-received key and guest keystore entry issues a local witness. Neither fixture keys nor raw logs are published. Changing the lab key, SDK binary or connection code requires requalification; an unpinned binary is refused outright.
2. **Set the local exclusions:** the private `~/.local/state/cleanyfin/adb-lab/blocked-hosts` must contain one forbidden numeric IPv4 address per line. It is provisioned on the project lab machine; no home address belongs in git. Missing, empty or malformed policy refuses real endpoints. Local state also holds the key and the pairing receipt; do not copy or publish it.
3. **Pair on request only:** first Forget the old PC in Settings → System → Developer options → Wireless debugging → Paired devices. Open **Pair device with pairing code**. `python3 -IB tools/playback-lab/adb_lab.py pair` asks for that screen's address and code; it never accepts a code in argv. Check **Paired devices** for `cleanyfin@lab`. Do not substitute the legacy port or a previously observed endpoint.
4. **Read:** `python3 -IB tools/playback-lab/adb_lab.py identify` takes the *different* debugging address on the main Wireless debugging screen, verifies `jarvis2` and the product model, and disconnects. For other measurements use `AdbLab.probe(name)` inside the context manager (see module docstring). Unknown probes are refused; there is no arbitrary shell, app access, capture, settings write, install or input command. Exit closes the transport; **Forget** the pairing when it is no longer wanted. Disconnect is not revocation.

Verified on 2026-11-25: the fresh API 36 Google TV image (revision 4) did not know the dedicated key before pairing. After native TLS pairing, Android's own `dumpsys adb` contained the matching key with the exact `cleanyfin@lab` comment. A fresh private server then reused the witness and listed zero attached devices. All 74 playback-lab unit tests passed. An earlier attempt waiting for a particular logcat line could not find the pairing listener; the working check can use the guest's change in listening sockets instead, without trying network ports.

This qualifies the connection, not any playback path. A reverse tunnel for a separately authorized playback test must explicitly reach its fixture from inside the private namespace. The older HDMI measurement below **does not yet use this identity guard**; do not run its legacy real-device connection against the household box.

### Real TV box: measure the borrowed onn. box's actual HDMI output

This runs the same measurements as the emulator, but against what the real box sends out of its HDMI port. The living-room onn. 4K Pro is borrowed for the session, then goes back. Nothing here connects to any device until you type in its pairing details, and the test server it uses is never visible on the home network.

**What to buy (once).** A USB 3.0 HDMI capture adapter: "USB 3.0", "1080p60" and "UVC" (works without drivers) on the box, MS2130 chip class, about $15–30. Avoid USB 2.0-only "4K" dongles: they compress 1080p60. If the adapter's USB id is not one the harness knows, `--preflight` lists it and you can name it with `--capture-usb VID:PID`.

**On the day (about 45 minutes, most of it hands-off):**

1. **Wire it.** Unplug the onn. box from the TV and bring it, its power supply and remote to this PC. Box HDMI → adapter HDMI in. Adapter USB → a blue (USB 3) port on this PC. Plug the box into power. It joins the home Wi-Fi as usual. No TV is needed; the adapter is the screen.
2. **Check this PC sees the adapter.** Run `python3 -I tools/playback-lab/tv-harness.py --preflight`. It changes nothing; it should print `Capture adapter: …` with the mode it would use.
3. **Turn on wireless debugging on the box.** You need a screen for this one step: plug the box into any nearby monitor or TV, or watch it through the adapter with any camera app. On the box: Settings → System → About → highlight **Android TV OS build** and press OK seven times ("You are now a developer"). Back to Settings → System → **Developer options** → turn on **Wireless debugging**, open it, choose **Pair device with pairing code**. Leave that screen open: it shows a six-digit code and an IP address & port. The Wireless debugging screen itself shows a second IP address & port.
4. **Run the measurement.** From the repository root: `python3 -I tools/playback-lab/tv-harness.py --device`. It asks for the pairing address, the six-digit code (typed hidden) and the debugging address. They are used for this run only and never written to disk or logs. It checks the box is an onn. Google TV before doing anything, prints what it found, and stops if it is anything else.
5. **Put it back.** At the end it asks whether to keep Wholphin on the box (press Enter to keep it; its test data is already cleared). Then on the box: Settings → System → Developer options → turn **Wireless debugging** off. Plug the box back into the living-room TV.

**What it changes on the box, and how it puts it back.** Before changing anything it records the installed apps (names and versions only), the HDMI audio format, the match-content frame-rate setting, the media volume and whether Wholphin is there. If Wholphin is already installed it stops, so the family's own copy is never touched. It then installs the unmodified Wholphin 1.1.2 (selected from the device’s ordered userspace ABIs and checked against the published SHA-256), sets HDMI audio to decoded PCM, turns frame-rate matching off so the adapter always sees a steady 60 Hz signal, raises the media volume, and inside Wholphin adds a separate lab server and sets its MPV player options. It never signs in or out of any Google or other account, never opens other apps or their data, and never changes home-screen or parental settings. At the end it clears Wholphin's data (the lab server entry, sign-in and options go with it), puts every recorded setting back, uninstalls Wholphin only if you say so, and prints a before/after comparison. `Box put back: True` with no differences (or only "Wholphin added", if you kept it) is the proof. If the connection drops before that, it prints the two things to undo by hand.

**What it measures.** The same claims as the emulator mode: filtered handoff, uncut picture and sound controls (all 500 frames in order including 126 marked; the identifiable-sample AAC and FLAC fixtures for bit-exactness and constant delay), then kept and marked picture and sound at the join, real-speed stall, seeks and persisted resume. The adapter's picture is stored as 320×180 grey frames, audio as 48 kHz stereo 16-bit from the adapter's own sound device only. Every take checks that decoded stereo PCM actually arrived (not a passed-through bitstream). The desktop's speakers and microphone are never used, and the run checks they are unchanged. The result is an experimental candidate row for the exact box, firmware, app, backend, output mode and plugin build measured; never an eligible one.

**Dry runs without the hardware.** `tools/playback-lab/hdmi-sim.py NEW_DIRECTORY` writes HDMI-shaped capture files (1080p60 cadence, exact PCM with a constant delay). `tv-harness.py --device --dry-run-emulator --capture-file DIR/control.mkv --capture-file filtered=DIR/filtered.mkv …` drives the harness's own emulator through the device path over adb TCP and scores those files. A dry run never writes a candidate row. `python3 -m unittest test_tv_device` (from `tools/playback-lab`) covers adapter discovery, mode choice, identity refusal, the change manifest and restore.

### Household marking, end to end

Run `python3 tools/playback-lab/check-plugin.py --case marking [--jellyfin 10.11|12.4]`. Extra prerequisites: Node 22 and a Chromium build (the newest `~/.cache/ms-playwright/chromium-*`, or `CLEANYFIN_CHROMIUM=/path/to/chrome`). `marking-browser.mjs` drives the plugin's own pages in a fresh, private headless profile over `--remote-debugging-pipe` (no debugging port); the browser reaches only `127.0.0.1`, where the runner forwards each connection into the network-less lab container with `docker exec` (nothing is published). Passwords go to the browser on stdin.

1. **Roles and bypasses over HTTP:** default roles from Jellyfin's administrator flag, then `governance.json` authority; anonymous, API-key, other-author, other-server, hidden-item, malformed, oversized, suggester-surface, stale-revision and body-carried actor/state attempts are refused; markers draft and edit their own proposed marks but cannot accept, reject, withdraw or publish; the second-reviewer setting refuses self-acceptance.
2. **Phone page** (390×844): the account's "TV" session plays the original; Start → Violence → End, Mark, then Language while the browser is offline. All three captures reach the store; the offline one only after reconnect.
3. **Review page timing:** with an empty timing register the page refuses exact boundaries. It then seeks, steps and nudges through 64 positions of the barcode fixture (keyframes, B-frames, both scene boundaries, both ends, 20 seeded random frames); each time the page's claimed frame and source millisecond must equal the barcode decoded from the presented pixels. The passing row is printed as `Timing register row:` for `delivery/evidence/review-timing-v1.json`.
4. **Refine, accept, publish from the page** as the administrator: step until the picture turns red (frame 137) and back from green (last red, 262), `I`/`O`, `5`, `S`×4, `Enter`, `A`, Publish. The stored mark must be `[5480, 10520)` violence/2/skip by the administrator, and the snapshot must bind the original's SHA-256.
5. **The existing shelf plays it:** reconcile gives one pointer; the projection and mpv handoff must keep all 374 unmarked frames, show zero marked frames and match the PCM sample-exactly.
6. **Audit:** the chain and `audit.head` must match the disk; a rewritten line, a dropped newest line and a removed head each refuse every call (and publishing) until restored. Editing the accepted mark empties the next snapshot and withdraws the shelf. The server log must contain no `ApiKey=`.

### Household file binding

Run `python3 tools/playback-lab/check-plugin.py --case household-binding [--jellyfin 10.11|12.4]` (same prerequisites as `marking`). The movie is an ordinary file in a folder mount (`/media/movies/Lab Movie (2026)/…mp4`), not the individually pinned fixture inode, so it goes through the household verifier: the plugin hashes it in the background (paced to 100 kB/s here so progress is visible), the review page shows the check, a marker drafts, the administrator refines frame-exactly, accepts and publishes, and mpv plays the filtered item with the same sample-exact checks as above. Then the runner touches the file (offer refused at once, same edition after the re-hash, same filtered item plays again) and replaces it with a same-size, same-duration copy with the mtime preserved (offer refused at once, filtered item withdrawn, the mark flagged "file changed, review again", publish refused until it is withdrawn). The file's bytes are the hard fixture's because filtered playback is only offered for a measured stream layout; the other measured layouts are exercised by the [format matrix](#common-household-layouts-format-matrix). The screenshot `household-review-again.png` is written to the marking design folder.

### Common household layouts (format matrix)

Run `python3 tools/playback-lab/format-matrix.py` from the repository root (same prerequisites as `household-binding`, minus Node and Chromium, plus NumPy and SciPy on the host). The R22/R23 cohort is eight Dolby layouts, FLAC, four standard AAC layouts and the original hard-fixture AAC. The generator (`format_fixtures.py`) supports:

- containers: MKV and MP4
- video: H.264 8-bit, HEVC Main 10, one HDR10-tagged HEVC
- sound: AAC-LC stereo, AC-3 5.1, E-AC-3 5.1, FLAC, Opus
- embedded subtitles over E-AC-3 5.1: MKV with a default SubRip track and alternate AAC sound; MKV with forced English ASS and manually selectable SubRip; MP4 with default plain `mov_text`

The generator refuses a layout unless the cut lies inside a GOP and inside an audio packet. For each Jellyfin line it starts one disposable loopback server and measures the layouts **one at a time**. Each measurement goes through the household verifier, a published mark, the plugin's real PlaybackInfo and the ticketed cut list, with mpv in the server's private namespace (`format_measure.py`).

Admission uses the [R22 viewer rule as amended by R23](../../knowledge-base/01-working/common-formats-2026-11-24/02-boundary-sweep.md). Joint picture/PCM captures and timestamps cover straight cuts, fresh starts around the join and one in-session resume after near-join paused seeks. R22 requires zero marked frames or samples, no added silence or high-frequency pop, intact kept picture, A/V within uncut jitter in 100 ms, and no more than 40 ms of kept sound lost. Ambiguous identity never passes. R23 drops only the first presented sample from the onset transient window for starts or resumes targeting the join itself. The sample must still be proven kept, the one-extra-kept-sample cap remains, and splice and offset-start comparisons are unchanged. Only passing Dolby tuples are candidates for desktop-mpv `experimental` rows; no TV, HDMI, passthrough or persisted-resume claim.

For R19, the uncut control must display every authored cue. The filtered take must show only the safe tracks with the expected default/forced flags, hide every cue inside, across or touching a mark, and keep the other cues at the expected time (25 fps observation resolution). The runner seeks across the join, also switches to the alternate subtitle track after load, and runs the viewer-rule picture/PCM checks for each selection. Bitmap tracks are refused, not measured as supported.

The full sweep tests all 24 positions without stopping at the first mismatch; a timed-out take is **unmeasured**, never a pass. `--case-timeout` sets the per-take limit. For the two server lines and the full R22/R23 cohort, run `python3 tools/playback-lab/format-matrix.py --jellyfin both --receipt RECEIPT.json --rows CANDIDATES.json`. Repeated `--layout` and `--local` (plain files, no Jellyfin) narrow a run. `--positions` and `--stop-on-fail` are diagnostics and a partial sweep never admits. The full JSON redacts capabilities; `--rows` writes candidates only. The runner never edits the reviewed register.

The [historical common-format results](../../knowledge-base/01-working/common-formats-2026-11-24/01-common-formats.md) predate the full sweep. The [R19 receipt](prototypes/common-formats/receipt-r19-2026-11-25.json) reported exact playback at the original single mark for all three subtitle layouts on Jellyfin 10.11.11 and 12.4.0. With each tested subtitle track selected, joint playback kept all 374 pictures and all six PCM channels exactly. Paused playback also verified an in-player switch to the alternate SubRip track. No cue inside, across or touching the cut appeared. The multi-audio MKV result measures only the default E-AC-3 sound track, not switched AAC. Across all 14 layouts, eight were exact and six stayed refused on each line. This is desktop mpv decoding to PCM, not a TV app, HDMI output or passthrough.

## Browser playback: original vs. filtered timeline

Run `python3 tools/playback-lab/serve-web.py`, open the printed loopback URL in Chromium, and choose **Run playback checks**. This generates a temporary compressed clip, a packaging index and an exact-source cut plan. The command serves only that temporary lab until Ctrl-C. There is no household library scan, edited movie on disk, or AI dependency.

The original control must show the red scene and its tone. The experimental player omits its entire encoded fragment from the browser's media buffer, preserves the blue and green sections and their tones, and maps a seek into the omitted scene to the start of green. The checks report sampled colors, dominant tones, duration and seek landing. They are **not** a proof of zero audio samples or compatibility with stock Jellyfin Web. Unsupported codecs, a wrong source, and unaligned timestamps must not quietly switch to unfiltered playback.

For an integration check in a **disposable loopback Jellyfin 10.11.11 lab only**: generate the bundle with `web-fixture.py NEW_DIRECTORY`; index its `Fixture.mp4` in the synthetic test library; put the generated HTML, JS and JSON assets under a separate lab path in the container web root. Load the page with `?item=<fixture item ID>`. It uses the passwordless, non-admin lab user `Viewer` to fetch the original through Jellyfin's direct stream endpoint. Do not configure an existing household server this way. This is a separate client, not a change to the stock player. See the [client evidence and constraints](../../knowledge-base/01-working/long-term-architecture-2026-10-07/10-client-boundary-and-browser-proof.md).

**R24 internal device dry run (synthetic only).** `tv-harness.py --device --r24 --dry-run-emulator --no-capture --frame-rate-match leave` uses the disposable private-namespace AVD and the pinned x86_64 release from `CLEANYFIN_APK_FEED` (default `~/.cache/cleanyfin-scratch/apks`). It contacts no physical device. The corresponding physical path is interlocked on a local dry-run receipt with both uncut presentation/PCM controls and verified teardown for this harness. That interlock proves recording readiness, not filtered playback: actual admission needs all 24 positions on the exact tuple. No v1 candidate or supplemental row is installed by this command. See the [owner runbook](../../knowledge-base/01-working/common-formats-2026-11-24/04-tv-test-runbook.md).
