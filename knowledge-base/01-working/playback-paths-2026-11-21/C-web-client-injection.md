# Path C: exact filtering inside the Jellyfin Web player (and its wrappers)

Research pass, 2026-11-21. No code run, no container started, no household device contacted. Claim tags: **VERIFIED-FROM-SOURCE** (I read the pinned file or spec text this session), **DOCUMENTED** (a maintainer README, release note or issue says so; not independently exercised), **INFERRED** (my reasoning from the above; needs a lab measurement).

Owner's pass rule (carried over from the lab notes): any detected marked picture or sound is a failure; material outside the mark is preserved; no trim margin is approved; dialogue filtering eventually needs mute, not only cut.

## 1. Verdict in one table

| Question | Answer |
| --- | --- |
| Can code be put into stock Jellyfin Web 10.11.11 from a server plugin without forking the client? | Yes. Two maintained mechanisms exist (JS Injector 4.x, File Transformation 3.x). Both are third-party plugins, not Jellyfin-supported APIs. |
| Can that code make a **cut** exact inside a GOP while the stock player keeps playing? | No, not by touching the stock element. It needs a replacement playback engine (MSE with sample-level trimming, or WebCodecs). That is a new player, not an injection. |
| Can it make a **mute** exact? | Plausibly on desktop Chromium with a calibrated Web Audio gain schedule, but zero-leak is unproven and depends on a clock mapping the platform does not guarantee. A pre-baked silent buffer removes the timing risk but costs a custom audio pipeline. |
| Do wrappers inherit it? | Browsers: yes. Jellyfin Desktop and Android (ExoPlayer mode): the page is inherited but the media element is not the thing that plays video, so element-level tricks do not apply. webOS: hosted page, likely yes. Tizen: bundled web build, no. Google TV: no usable wrapper. |

### Why native skip leaks (explains the lab's four frames)

The native segment manager acts inside `onPlayerTimeUpdate`, which is driven by the element's `timeupdate` event ([mediaSegmentManager.ts](https://github.com/jellyfin/jellyfin-web/blob/v10.11.11/src/apps/stable/features/playback/utils/mediaSegmentManager.ts), `onPlayerTimeUpdate`; player binding at [plugin.js L1650](https://github.com/jellyfin/jellyfin-web/blob/v10.11.11/src/plugins/htmlVideoPlayer/plugin.js#L1650)). It checks "current time falls within a segment" and only then calls `playbackManager.seek`. The HTML spec says `timeupdate` during normal playback fires when none was fired in the past 15 to 250 ms, "not faster than about 66Hz or slower than 4Hz" ([HTML source, media element time-update steps](https://html.spec.whatwg.org/multipage/media.html#event-media-timeupdate)). **VERIFIED-FROM-SOURCE** for both texts. That the lab's four red frames (160 ms at 25 fps) are this cadence plus seek latency is **INFERRED**, though consistent.

Consequence: any injected scheduler built on `timeupdate` has the same flaw. Using `requestVideoFrameCallback` narrows it to about one frame, but see section 4.

## 4. Frame-accurate techniques available in a browser

The core problem, already shown in the lab: marks fall inside GOPs, so the first allowed picture after a cut is usually not a keyframe.

### 4.1 Spec text behind the lab's "lost ten allowed frames"

The MSE coded-frame-processing algorithm says: a frame whose presentation timestamp is below `appendWindowStart` is dropped and the track buffer's **need random access point flag** is set to true; while that flag is set, any frame that is not a random access point is dropped. The spec's note says collecting pre-window frames to splice at the first in-window non-RAP frame "requires multiple decoders or faster than real-time decoding so for now this behavior will not be a normative requirement". ([media-source-respec.html L3965-L4000](https://github.com/w3c/media-source/blob/main/media-source-respec.html), read from main on 2026-11-21.) **VERIFIED-FROM-SOURCE.** This is exactly the lab's negative control: with the start-of-window at the cut end, every frame until the next keyframe is dropped, giving a gap of allowed frames. The end side does not have the problem, because `appendWindowEnd` drops frames whose end exceeds the window and sets the RAP flag, which only discards material after the cut (INFERRED: unless B-frame reordering makes earlier-presented frames depend on dropped later ones; the lab fixture did not exercise that).

## 7. Verdicts

**Cut: not viable as an injection into the stock player; viable only as a replacement engine.**
- Stock player plus script: leaks at least one frame and risks removing allowed frames (sections 2 and 4 A). Does not meet the owner's pass rule.
- hls.js playlist rewrite: exact only on segment boundaries, which Jellyfin sets at multiples of the segment length (6 s in the logs I found); arbitrary marks fail. Unusable for direct play.
- MSE alone cannot produce sample-exact starts after a cut (spec text above, matched by the lab). MSE plus a server-supplied re-encoded boundary (for example a second transcode started at the cut end) **might** work; this is untested.
- WebCodecs is the only technique here that is exact by construction, but it is a new player with weak codec coverage (no AC-3/E-AC-3/DTS in the registry), and it still would not reach Android ExoPlayer, desktop mpv, Tizen, or Google TV. Verdict: a research-grade player, not a quick win. **Not recommended as the product path; keep as an optional last-resort browser adapter.**

**Mute: viable as a limited, browser-only experiment; not yet a pass.**
- Mechanically simple. Whether zero marked audio is audible cannot be known without measuring the media-to-audio clock error on target browsers.
- If that error is a few milliseconds and a calibration is accepted, it passes only in desktop Chromium-class browsers, not on the wrappers that matter (ExoPlayer, mpv, TV platforms).
- The robust variant (bake silence into decoded audio) removes the timing risk but is the same size as a custom audio player.

Combined with the owner's household TV target, **path C is a prototype-grade web adapter, not the default route** to meeting the gate.

## 8. Smallest lab prototype that proves or kills path C

Disposable `jellyfin/jellyfin:10.11.11` container, the existing synthetic fixtures (three-section 25 fps, 440/880/660 Hz), non-admin `Viewer`, desktop Chromium. No household media, no network exposure.

1. **Delivery proof (about half a day).** Put a ~40-line script in the web root and load it through the plugin route (File Transformation or JS Injector in the container, or a tiny custom middleware): assert it runs before the bundle, that `window.Hls`, `window.Events`, `window.ApiClient` exist, and that a `config.json` entry naming a window-global media-player plugin gets `playbackManager`. Record whether the race works with JS Injector's loader. Pass: all globals visible and plugin registered. Kill: cannot get the global before `loadPlugins` and no DOM-only path works.
2. **Mute experiment (about 1 to 2 days).** Fixture: marked section with a 1 kHz tone and allowed 440 Hz tone immediately on both sides, with sample-exact edges. Injected script: `AudioContext`, `createMediaElementSource(video)`, gain node, per-frame mapping from `rVFC` and `getOutputTimestamp()`, schedule gain 0 at the mark start and 1 at the end. Measure in-page with an `AnalyserNode` or `AudioWorklet` on the same graph: leaked marked samples, lost allowed samples, in each of: cold play, pause/resume, seek into and out of the mark, 1.5x rate, hidden tab for 10 s, buffering stall (throttled network), direct-play MP4 and HLS transcode. Report the measured edge error in samples per scenario. Pass: zero marked-tone energy and allowed tones intact within a stated bound in every non-hidden scenario. Kill: any scenario leaks above the noise floor of the offline control.
3. **Cut experiment, the single decisive one (about 3 to 5 days).** Build a minimal WebCodecs adapter for one H.264/AAC MP4 fixture whose cut falls inside a GOP with distinct witness pictures adjacent to the mark: mp4box.js demux, decode from the preceding keyframe, drop frames by PTS, `AudioData` trimmed to sample counts, canvas out, audio-clock master. Measure frame-by-frame against the lossless reference from `check-cut.py`: marked frames shown (target 0), allowed frames lost (target 0), audio samples exact, A/V skew, seek and CPU cost. In parallel check one MSE variant with a second Jellyfin transcode started at the cut end, appended with `timestampOffset`, to see whether Jellyfin's `StartTimeTicks` yields a frame-exact first frame (open unknown below).
4. **Decision rule.** If step 3's WebCodecs adapter hits zero and zero, record that the web path is technically possible and carry it as an optional browser adapter; if step 2 meets the bound, mute-only ships for browsers. Otherwise path C is closed and the project proceeds without a client-side filter.

**Estimated build effort.** Delivery proof 0.5 day; mute experiment 1 to 2 days; WebCodecs cut adapter 3 to 5 days for the single-fixture proof; the MSE-plus-second-transcode comparison 1 to 2 days. A productized browser adapter (seeking, tracks, subtitles, HDR, updates when Jellyfin changes) is weeks, plus recurring per-release maintenance. These are my estimates (INFERRED).
